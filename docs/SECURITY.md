# Linkora Security Architecture & Threat Model

## 1. Core Cryptographic Primitives

- **Key Agreement**: Elliptic Curve Diffie-Hellman over NIST P-256 (`secp256r1`).
- **Symmetric Encryption**: AES-256-GCM (Authenticated Encryption with Associated Data).
- **Key Derivation**: HKDF-SHA256 (RFC 5869).
- **Signatures**: ECDSA with SHA-256 using hardware security modules:
  - Apple: Apple Secure Enclave (`kSecAttrTokenIDSecureEnclave` on iPhone & Mac).
  - Android: Android Keystore (`KeyProperties.SECURITY_LEVEL_STRONGBOX` or `TRUSTED_ENVIRONMENT`).
- **Integrity Digest**: SHA-256 rolling hash.

## 2. Threat Model & Mitigations

### A. Eavesdropping on Local Wi-Fi
- **Risk**: Unencrypted local network packets can be sniffed on public or untrusted Wi-Fi.
- **Mitigation**: Every packet following the initial handshake is encrypted with AES-256-GCM. An attacker listening on the Wi-Fi sees only high-entropy ciphertext.

### B. Man-in-the-Middle (MitM) Attacks
- **Risk**: An active attacker alters public keys in transit during discovery.
- **Mitigation**: Out-of-Band (OOB) authentication via dynamic QR code containing the peer's public key fingerprint and a 6-digit SAS code derived from the ephemeral shared secret. The connection is aborted unless both devices acknowledge identical SAS codes.

### C. Replay Attacks
- **Risk**: An attacker captures a valid biometric approval message and replays it later to unlock the Mac.
- **Mitigation**: Every `AUTH_CHALLENGE_REQUEST` contains a cryptographically secure 32-byte nonce generated by the Mac, valid for only 60 seconds. Once consumed, the nonce is stored in a consumed-nonce cache and rejected if presented again.

### D. Clipboard Loops & Leakage
- **Risk**: Device A copies text, syncs to Device B, which detects a clipboard change and syncs it back to Device A indefinitely.
- **Mitigation**: Every clipboard item carries a SHA-256 digest. When Linkora writes a remote item to the local pasteboard, that hash is stored in a local suppress-set. Outgoing broadcasts are triggered only for novel hashes not in the suppress-set.

## 3. macOS Login Window Reality & Engineering Truth

### What is Legally and Safely Possible:
1. **App-Level Session Lock**: Linkora locks its own session, hides sensitive files, pauses clipboard sync, and requires biometric approval from the paired phone before unlocking.
2. **Mac Screen Lock**: Linkora can safely trigger native macOS screen sleep or immediate screen locking via `SACLockScreenImmediate`.

### What is Impossible via Public APIs (and Why Linkora Refuses to Fake It):
- **Bypassing the macOS Loginwindow / FileVault**:
  - macOS 12+ (Monterey), 13 (Ventura), 14 (Sonoma), and 15 (Sequoia) run the `loginwindow` inside a dedicated, isolated Mach bootstrap sandbox protected by System Integrity Protection (SIP).
  - No public API allows a non-root user process to unlock the system login screen without typing the user's password.
  - **Insecure hacks rejected by Linkora**:
    1. *Storing the user's plaintext password*: Extremely dangerous; exposes credentials to malware.
    2. *Synthetic Accessibility typing on login screen*: Blocked by macOS; `CGEvent` is disabled on the secure login session.
    3. *Custom PAM modules (`/etc/pam.d/authorization`)*: Can brick macOS authentication after OS updates and cannot reliably establish network connections to third-party mobile apps before user login.
- **Linkora's Honest Design**: Phone biometric approval unlocks Linkora-gated resources and companion workflows, while clearly informing the user of native macOS boundaries.
